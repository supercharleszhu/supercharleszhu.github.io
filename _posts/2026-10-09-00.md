## Why this post

While writing a simple CuTe DSL matrix-multiplication kernel, I compared its
output against `torch.mm` and saw this:

```text
Mismatched elements: 415836 / 67108864 (0.6%)
Greatest absolute difference: 0.0924
Greatest relative difference: 5715.5
```

The kernel's indexing was correct. Every output element was written exactly
once. The problem was that "FP16 GEMM" did not specify enough information to
define the expected answer.

A GEMM precision contract has at least four separate choices:

1. the storage type of A and B;
2. the precision used to multiply A and B;
3. the precision used to accumulate the products;
4. the storage type of the final output.

Two kernels can implement the same equation and still return different
bit patterns because they make different choices at any of those stages. Even
when all four choices agree, a different reduction order can change the final
rounded result.

This post develops a practical model for reasoning about those differences,
constructing the right PyTorch reference, and deciding whether a mismatch is a
real correctness bug or expected floating-point behavior.

---

## 1. A dtype does not completely describe an operation

Consider the GEMM

$$
C_{m,n} = \sum_{k=0}^{K-1} A_{m,k}B_{k,n}.
$$

Calling this an "FP16 GEMM" could mean any of the following:

```text
FP16 input x FP16 input -> FP16 accumulation -> FP16 output
FP16 input x FP16 input -> FP32 accumulation -> FP16 output
FP16 input x FP16 input -> FP32 accumulation -> FP32 output
```

The second and third contracts are common on NVIDIA Tensor Cores. A and B are
stored as FP16, while their products are accumulated into FP32 registers or
architecture-specific accumulator storage. The result may remain FP32 or be
rounded to FP16 in the epilogue.

This distinction matters because accumulation performs $K-1$ additions for
every output element. For an `8192 x 8192 x 8192` GEMM, each output is the sum
of 8192 products. Small rounding differences have thousands of opportunities
to enter the result.

### Precision is a pipeline

A useful way to describe a kernel is:

```text
input storage
  -> operand conversion
  -> multiply
  -> accumulation
  -> epilogue conversion
  -> output storage
```

For example:

```text
FP16 storage
  -> exact conversion to FP32
  -> FP32 multiply
  -> FP32 accumulation
  -> no conversion
  -> FP32 output
```

is not the same arithmetic contract as:

```text
FP16 storage
  -> FP16 multiply and rounding
  -> FP32 accumulation
  -> no conversion
  -> FP32 output
```

In the second contract, FP32 accumulation cannot recover bits that were already
discarded when each product was rounded to FP16.

## 2. The formats: FP16, BF16, TF32, and FP32

The exponent determines range. The significand determines precision.

| Format | Exponent bits | Fraction bits | Effective precision | Approximate decimal digits |
| --- | ---: | ---: | ---: | ---: |
| FP16 | 5 | 10 | 11 bits | 3.3 |
| BF16 | 8 | 7 | 8 bits | 2.4 |
| TF32 | 8 | 10 | 11 bits | 3.3 |
| FP32 | 8 | 23 | 24 bits | 7.2 |

The hidden leading bit is why effective precision is one bit greater than the
stored fraction width for normal values.

Several consequences follow:

- FP16 has more significand precision than BF16, but much less exponent range.
- BF16 has approximately the same exponent range as FP32, making it harder to
  overflow or underflow during training.
- TF32 has FP32-like range and FP16-like precision. It is an arithmetic mode
  for Tensor Core computation, not a normal PyTorch tensor storage dtype.
- FP32 has enough significand bits to represent every finite FP16 value exactly.

That final point explains an important PyTorch behavior:

```python
A_fp32 = A_fp16.float()
```

This conversion does not invent new information, but it also does not introduce
new rounding error. Every FP16 value is exactly representable in FP32.

## 3. Three PyTorch expressions that look similar but are not

Suppose `A` and `B` are FP16 tensors.

### Convert before GEMM

```python
reference_fp32 = A.float() @ B.float()
```

Both FP16 inputs are converted exactly to FP32 before matrix multiplication.
The returned tensor is FP32.

### Convert after GEMM

```python
reference_rounded = (A @ B).float()
```

The GEMM returns an FP16 tensor because its inputs are FP16. Converting that
result to FP32 happens after the output has already been rounded to FP16.
`.float()` cannot restore the discarded bits.

### Keep the FP16 output

```python
reference_fp16 = A @ B
```

This is appropriate when the custom kernel also writes an FP16 output. It is
not the appropriate reference for a kernel that intentionally exposes its FP32
accumulator without an FP16 epilogue conversion.

The order of conversion is therefore part of the test:

```text
A.float() @ B.float()
```

and

```text
(A @ B).float()
```

have the same final PyTorch dtype but do not compute the same result.

## 4. What FP16 input with FP32 accumulation means

Modern mixed-precision GEMM normally uses low-precision storage and
high-precision accumulation:

```text
A operand:    FP16
B operand:    FP16
accumulator:  FP32
output:       FP16 or FP32
```

Tensor Core instructions are designed around this pattern. Conceptually, each
operation is:

$$
d = a \times b + c
$$

where `a` and `b` are low-precision operands and `c` and `d` are FP32
accumulators.

The phrase "FP16 multiplication" can be misleading. There are two different
possibilities:

1. accept FP16 inputs and form a product suitable for an FP32 fused
   multiply-add;
2. compute a product and round that product back to FP16 before converting it
   to FP32 for accumulation.

The first is the usual mixed-precision MMA contract. The second loses more
information.

In a scalar CuTe DSL kernel, make the intended contract explicit:

```python
acc = cutlass.Float32(0.0)

for k in cutlass.range(0, K):
    a = cutlass.Float32(A[row, k])
    b = cutlass.Float32(B[k, col])
    acc += a * b

C[row, col] = acc
```

This says:

```text
FP16 storage -> FP32 operands -> FP32 accumulation -> FP32 output
```

By contrast:

```python
acc += A[row, k] * B[k, col]
```

leaves the expression's promotion and product type to the DSL's type rules.
Even though `acc` is FP32, the product may already have been rounded before it
is added. An FP32 destination does not automatically guarantee an FP32
multiply.

## 5. Why matching precision still does not guarantee matching bits

Floating-point addition is not associative:

$$
(a+b)+c \ne a+(b+c).
$$

The real-number expressions are equivalent, but finite-precision rounding
happens after each operation.

A simple scalar kernel might accumulate in strict K order:

```text
acc = (((p0 + p1) + p2) + p3) + ...
```

A high-performance library GEMM partitions K and uses a tree or tiled
reduction:

```text
partial0 = p0 + p1 + ...
partial1 = p32 + p33 + ...
result = partial0 + partial1 + ...
```

Tensor Core instructions further group products into fixed MMA shapes.
Split-K kernels may combine partial results from multiple CTAs. Persistent
kernels and architecture-specific implementations may choose yet another
schedule.

All can be correct implementations of GEMM. They need not be bitwise equal.

The difference generally grows with:

- larger K;
- larger input magnitudes;
- cancellation between positive and negative terms;
- lower product or accumulator precision;
- more independently reduced partial sums.

That is why a small `128 x 128 x 128` correctness test and an
`8192 x 8192 x 8192` stress test can require different absolute tolerances.

## 6. TF32 can silently change an FP32 reference

On NVIDIA GPUs, an FP32 PyTorch GEMM may use TF32 Tensor Core arithmetic,
depending on the PyTorch version and backend settings. TF32 keeps FP32's
exponent range but uses a shorter significand for multiplication.

If the custom kernel performs IEEE FP32 multiplication and accumulation, make
the reference contract explicit:

```python
torch.backends.cuda.matmul.allow_tf32 = False
reference = A.float() @ B.float()
```

Newer PyTorch releases also expose more explicit FP32 precision controls. The
exact API is version-dependent, so inspect the active PyTorch documentation and
settings when reproducibility matters.

The important point is conceptual:

```text
torch.float32 tensor
```

does not, by itself, prove that every multiplication used the full FP32
significand on every backend.

## 7. Reading `torch.testing.assert_close`

An approximate comparison normally accepts an element when:

$$
|actual-expected| \le atol + rtol \times |expected|.
$$

For example:

```python
torch.testing.assert_close(
    actual,
    expected,
    rtol=1e-3,
    atol=1e-2,
)
```

The relative term scales with the expected value. The absolute term protects
the comparison near zero.

### Why relative error can look absurd

Suppose:

```text
expected = 0.000001
actual   = 0.002
```

The absolute error is approximately `0.002`, but the relative error is roughly
2000. A reported relative error in the thousands does not automatically mean
the kernel produced a huge value. It often means the expected value was very
close to zero.

For GEMMs with cancellation, always inspect both absolute and relative
statistics.

### Do not choose tolerances only to make the test pass

A tolerance is part of the numerical specification. It should follow from:

- the input dtype;
- the accumulator dtype;
- the output dtype;
- K;
- the expected scale of the result;
- the reduction algorithm;
- the downstream application's sensitivity.

Start with a known precision contract, measure the error distribution, and then
choose a tolerance that detects regressions without demanding impossible
bitwise agreement.

## 8. A practical error report

One assertion message is not enough to understand numerical behavior. Report
the distribution:

```python
def report_error(actual: torch.Tensor, expected: torch.Tensor) -> None:
    actual = actual.float()
    expected = expected.float()
    absolute = (actual - expected).abs()

    denominator = expected.norm().clamp_min(torch.finfo(torch.float32).tiny)
    relative_l2 = (actual - expected).norm() / denominator

    print(f"max absolute error:  {absolute.max().item():.6g}")
    print(f"mean absolute error: {absolute.mean().item():.6g}")
    print(f"p99 absolute error:  {torch.quantile(absolute, 0.99).item():.6g}")
    print(f"relative L2 error:   {relative_l2.item():.6g}")
```

These metrics answer different questions:

| Metric | What it reveals |
| --- | --- |
| Maximum absolute error | The worst individual output. |
| Mean absolute error | Whether error is widespread or isolated. |
| P99 absolute error | A robust high-percentile view that ignores a few extreme elements. |
| Relative L2 error | Overall error energy relative to the reference. |
| Mismatch percentage | How much of the output violates the chosen contract. |

For the motivating `8192^3` test, only about 0.6% of elements violated
`rtol=0.01, atol=0.01`, and the maximum absolute difference was around 0.1.
That pattern is very different from a layout bug, which usually produces large,
structured, and widespread errors.

## 9. Construct the reference from the kernel contract

There is no single universal reference. Choose one that matches the kernel.

### FP16 inputs, FP32 accumulator, FP32 output

```python
torch.backends.cuda.matmul.allow_tf32 = False
reference = A.float() @ B.float()

torch.testing.assert_close(
    C,
    reference,
    rtol=1e-3,
    atol=1e-2,
)
```

This is the most useful contract for validating a mixed-precision kernel before
the epilogue rounds its output.

The tolerance shown is a starting point, not a universal constant. Large K or a
different reduction tree may require a larger scale-aware absolute tolerance.

### FP16 inputs, FP32 accumulator, FP16 output

If the custom epilogue stores FP16:

```python
reference = A @ B

torch.testing.assert_close(
    C,
    reference,
    rtol=1e-2,
    atol=1e-2,
)
```

Both `C` and `reference` should be FP16 here.

If the kernel keeps FP32 internally but the intended public contract is FP16,
round the custom output before comparison:

```python
torch.testing.assert_close(
    C.float().half(),
    A @ B,
    rtol=1e-2,
    atol=1e-2,
)
```

This verifies the FP16-visible result, but it can hide smaller accumulator
errors that disappear during final FP16 rounding. Keep a separate FP32
accumulator test when possible.

### FP16-rounded products with FP32 accumulation

If a scalar teaching kernel intentionally rounds every product to FP16 before
adding it to an FP32 accumulator, construct that exact reference only at a
small size:

```python
reference = torch.zeros((M, N), device="cuda", dtype=torch.float32)

for k in range(K):
    product_fp16 = A[:, k:k+1] * B[k:k+1, :]
    reference += product_fp16.float()
```

This is slow because it launches many operations and materializes intermediate
tiles. It is a semantic reference, not a benchmark implementation.

## 10. Separate mapping tests from numerical stress tests

One giant random test should not carry the entire correctness burden.

### Stage 1: exact mapping test

Use small integer-valued inputs that are exactly representable:

```python
M = N = K = 32

A = torch.randint(
    -2, 3, (M, K), device="cuda", dtype=torch.int32
).half()
B = torch.randint(
    -2, 3, (K, N), device="cuda", dtype=torch.int32
).half()
```

The values and small sums are exact in FP16 and FP32. This test catches:

- swapped M/N/K modes;
- incorrect strides;
- wrong block coordinates;
- incomplete output coverage;
- transposed operands;
- missing edge predication.

Use a tight comparison here.

### Stage 2: random small numerical test

Use `128^3` or `256^3`, compare against the intended high-precision reference,
and inspect the complete error distribution.

### Stage 3: awkward shapes

Test dimensions that are not multiples of the tile sizes:

```text
M=257, N=129, K=67
```

This isolates edge-predication and boundary errors.

### Stage 4: large-K stress test

Use a large K to expose accumulation behavior:

```text
M=512, N=512, K=8192
```

There is usually no need to allocate a full `8192^3` output just to study
accumulation error.

### Stage 5: performance shape

Only after correctness is established should the full benchmark shape be used.

## 11. Correctness and benchmarking should be separate phases

Compilation, correctness checking, and timing should not overlap.

```python
compiled = cute.compile(
    solve,
    A_cute,
    B_cute,
    C_cute,
    M,
    N,
    K,
)

# Correctness phase
compiled(A_cute, B_cute, C_cute, M, N, K)
torch.cuda.synchronize()

torch.backends.cuda.matmul.allow_tf32 = False
reference = A.float() @ B.float()
report_error(C, reference)
torch.testing.assert_close(C, reference, rtol=1e-3, atol=1e-2)

# Warmup phase
for _ in range(5):
    compiled(A_cute, B_cute, C_cute, M, N, K)
torch.cuda.synchronize()

# Timing phase
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
iterations = 20

start.record()
for _ in range(iterations):
    compiled(A_cute, B_cute, C_cute, M, N, K)
end.record()
torch.cuda.synchronize()

average_ms = start.elapsed_time(end) / iterations
tflops = 2 * M * N * K / (average_ms / 1000) / 1e12

print(f"latency: {average_ms:.3f} ms")
print(f"throughput: {tflops:.2f} TFLOP/s")
```

Compile before timing. Do not include `torch.mm`, allocation, random-number
generation, or synchronization beyond what the timing method requires.

## 12. A debugging checklist for GEMM mismatches

When a custom GEMM disagrees with PyTorch, check these in order.

### 1. Did the kernel actually run?

`torch.empty` returns uninitialized memory:

```python
C = torch.empty((M, N), device="cuda")
```

Checking `C` before launching the kernel can produce confusing partial matches
because the CUDA allocator may reuse old storage.

Always launch and synchronize before validation:

```python
compiled(...)
torch.cuda.synchronize()
```

### 2. Does every output have exactly one owner?

Verify:

- grid dimensions;
- threads per block;
- thread-to-output mapping;
- predicates for edge tiles;
- no duplicate writers.

Structured errors by row, column, tile, or boundary usually point to ownership
or layout problems rather than floating-point precision.

### 3. Are the logical shapes and strides correct?

Print both:

```python
print(A.shape, A.stride())
print(B.shape, B.stride())
print(C.shape, C.stride())
```

For CuTe, logical mode order and physical stride order are separate concepts.
A mathematically correct index expression can read the wrong storage if the
host view does not follow the expected layout.

### 4. What is the product type?

Do not infer it from the accumulator:

```python
acc = cutlass.Float32(0.0)
acc += A[...] * B[...]
```

Make conversions explicit when the contract matters.

### 5. What is the accumulator type?

FP16 accumulation across thousands of terms can lose substantial information.
Use FP32 accumulation for the standard mixed-precision GEMM contract.

### 6. What is the output type?

Comparing an FP32 accumulator against an FP16-rounded library result is not an
apples-to-apples comparison.

### 7. Is TF32 enabled?

An FP32 tensor does not guarantee IEEE FP32 multiplication on Tensor Cores.

### 8. Is the mismatch caused by reduction order?

If mapping tests pass, errors are small, and error locations appear random,
compare error statistics before assuming the kernel is wrong.

### 9. Is the tolerance scale-aware?

Near-zero expected values need an absolute tolerance. Large outputs can use the
relative term. Both are necessary for random GEMM data.

## 13. The central lesson

"The tensors are FP16" is not a complete numerical specification.

A useful kernel contract says:

```text
A/B storage:       FP16
operand compute:   FP32 conversion
accumulation:      FP32
output storage:    FP32
reduction:         serial K order
reference:         FP32 PyTorch GEMM with TF32 disabled
tolerance:         chosen from measured error at the target K and scale
```

Once those choices are explicit, most mysterious mismatches become ordinary:

- converting before versus after GEMM;
- FP16 output rounding;
- FP16-rounded products;
- TF32 reference computation;
- non-associative reduction order;
- unrealistic near-zero relative-error checks.

Numerical correctness on GPUs rarely means bitwise equality with one library
implementation. It means that the kernel follows a documented precision
contract, satisfies an error bound appropriate for that contract, and continues
to satisfy it across the shapes and value distributions the application
actually uses.
