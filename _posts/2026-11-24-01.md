## The question: how much of a TPU compiler can we actually read?

For NVIDIA GPUs, a developer can inspect Triton, MLIR, LLVM's NVPTX backend,
PTX, and often final SASS. The TPU software stack has a different boundary.

TorchTPU makes a large and useful part of the path open:

```text
PyTorch program
  -> ATen dispatcher or TorchDynamo FX graph
  -> TorchTPU deferred operations
  -> StableHLO MLIR
  -> PjRt client API
  -> libtpu
  -> TPU executable
```

The upper part is open source. The final compiler and machine interface are
not:

```text
open source                                  closed/proprietary
─────────────────────────────────────┬─────────────────────────────
PyTorch                              │
TorchDynamo / FX                     │
TorchTPU backend                     │
StableHLO                            │
OpenXLA interfaces and many passes   │
Pallas / Mosaic input dialect        │
PjRt API                             │ libtpu
                                     │ final TPU backend compilation
                                     │ TPU ISA and machine code
```

That means this cannot be the same kind of instruction-by-instruction tour as
the Triton-to-PTX post. We can follow a PyTorch operation all the way to
StableHLO, the `PJRT_Client_Compile` boundary, and a serialized Mosaic custom
call. We cannot inspect the production pass pipeline that converts those
inputs into TPU machine instructions.

This distinction is the most important conclusion of the source search:
**the TPU-facing interface is open, but the final TPU backend is not**.

## What the TorchTPU paper contributes

The paper presents TorchTPU as a native PyTorch backend rather than a wrapper
around JAX or the older lazy-tensor execution model. Its design goals are:

1. normal PyTorch device semantics through `.to("tpu")`;
2. useful eager execution instead of requiring full-graph compilation;
3. `torch.compile(..., backend="tpu")` through TorchDynamo;
4. PyTorch `ProcessGroup` integration for distributed collectives; and
5. access to optimized Pallas and library kernels when generated StableHLO is
   not sufficient.

The implementation is available at
[`google-pytorch/torch_tpu`](https://github.com/google-pytorch/torch_tpu).
The repository is Apache-2.0 licensed and contains the PyTorch integration,
eager runtime, deferred graph construction, StableHLO builders, compilation
cache, PjRt calls, distributed backend, and custom-kernel glue.

The paper's central architectural idea is **hybrid eager/compiled execution**:
every PyTorch operation can behave eagerly, but TorchTPU still represents and
compiles that operation through StableHLO. Multiple eager operations can also
be deferred and fused into a larger compilation unit.

## 1. The hardware model visible to the compiler

A TPU is not programmed as a grid of CUDA threads. The paper describes several
execution resources:

| TPU component | Typical work |
|---|---|
| MXU | Dense matrix multiplication on systolic arrays |
| VPU | Vector and elementwise operations |
| Scalar unit | Scalar control and arithmetic |
| SparseCore | Embedding, gather/scatter, and sparse workloads |
| DMA engines | Host/device and remote data movement |
| ICI | High-bandwidth interconnect within a TPU slice |
| DCN | Communication across slices |

The paper uses **TensorCore** to mean a TPU processor containing these
resources. This should not be confused with NVIDIA Tensor Cores.

The programmer normally does not directly select an MXU instruction. Instead,
the compiler receives tensor operations, layouts, shapes, sharding, and
precision requirements, then maps them onto these resources.

This makes high-level structure particularly important. StableHLO preserves
operations such as:

```text
dot_general
convolution
reduce
all_reduce
dynamic_slice
dynamic_update_slice
```

These are much closer to an ML graph than PTX instructions. The closed TPU
backend can use tensor shape and operation semantics to select implementation
strategies that would be difficult to recover from scalarized code.

## 2. TorchTPU enters through PyTorch's dispatcher

TorchTPU is implemented as a PyTorch `PrivateUse1` device backend. ATen
operations dispatched to a TPU tensor reach registrations such as:

[`csrc/eager/tpu_aten_kernels.cc`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/eager/tpu_aten_kernels.cc#L375)

```cpp
TORCH_LIBRARY_IMPL(aten, PrivateUse1, m) {
  ...
}
```

Instead of immediately running one hardware instruction, an eager operation
creates a deferred representation associated with a TPU device buffer. The
`DeferredOp` design is documented near
[`device_buffer.h:86-90`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/eager/device_buffer.h#L86-L90).

Operation-specific builders create StableHLO. For example, binary
multiplication is connected to `mlir::stablehlo::Mul` in
[`binary.cc`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/ops/binary.cc#L65):

```cpp
TT_BINARY_BUILDER_(BuildMulShlo, mlir::stablehlo::Mul);
```

The useful mental model is:

```text
aten::mul
  -> TorchTPU PrivateUse1 kernel
  -> deferred operation
  -> StableHLO builder
  -> materialization and compilation
```

This is still eager from the PyTorch user's perspective, even though each
operation passes through a compiler representation.

## 3. Eager execution is still compilation

The paper describes three user-facing eager behaviors:

- **Strict eager:** compile and launch operations individually;
- **Debug eager:** block so failures and stack traces are easier to localize;
- **DeferAndFuse:** accumulate operations until a materialization point and
  compile them together.

The C++ enum uses internal names including `kDeferAndFuse`, `kDeferNever`, and
`kDeferNeverAndLaunchBlocking`
([`eager_mode.h:23-45`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/eager/eager_mode.h#L23-L45)).

DeferAndFuse waits until an operation requires a concrete result. Examples of
materialization points include:

```python
x.cpu()
x.item()
print(x)
```

At materialization, TorchTPU:

1. walks the reachable deferred operations;
2. determines which values remain live outputs;
3. preserves side-effecting operations such as collectives;
4. computes a compilation-cache key;
5. reuses or compiles the StableHLO module; and
6. enqueues the resulting executable.

The central implementation is
[`Materialize()`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/eager/materialize.cc#L690-L735),
with deferred-node discovery earlier in the same file.

The paper reports DeferAndFuse as at least 50% faster than strict eager in its
tested cases, while also reducing peak HBM. The reason is familiar from GPU
compilers: a larger graph enables fusion, removes intermediate materialization,
and amortizes compilation and launch overhead.

### The compilation cache is part of execution semantics

Eager compilation would be unusable if every repeated operation triggered a
fresh compiler invocation. TorchTPU therefore uses a multi-tier cache:

1. process-local memory;
2. host shared memory; and
3. an optional remote filesystem such as GCS.

The source contains the main
[`CompilationCache`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/common/compilation_cache.h#L220)
and separate tier-two and tier-three implementations.

Shape, graph structure, compilation options, and software versions affect the
key. This is why apparently small changes can cause a TPU recompilation:

- a new tensor shape;
- different compile options;
- a different deferred graph;
- changed TorchTPU, libtpu, or PjRt versions; or
- a dynamic shape that cannot reuse a bounded executable.

## 4. PyTorch views versus StableHLO SSA

PyTorch permits storage aliasing and views. Operations such as transpose,
slice, expand, and `as_strided` can produce tensors that share underlying
storage.

StableHLO is value-oriented SSA. It does not expose a general mutable
`as_strided` storage view with arbitrary overlap. TorchTPU must therefore
translate PyTorch's storage semantics into functional tensor operations.

The paper describes view decomposition using combinations of:

```text
transpose
reshape
broadcast
slice
concatenate
bitcast
```

A read reconstructs the logical view from its base tensor. A write applies an
inverse transformation to produce a new base value, often using an operation
conceptually similar to `dynamic_update_slice`, then updates the storage to
refer to that new value.

This reveals a general compiler issue: a frontend's semantics do not always
fit the target IR directly. The backend must preserve user-visible behavior
while expressing it in legal target operations.

Overlapping or broadcasted writes remain difficult because a functional SSA
update needs an unambiguous mapping from view elements back to base storage.

The same functional model changes allocation. The paper says `torch.empty`
does not immediately allocate TPU memory; it becomes a deferred NaN fill.
Allocation is determined later by compilation and liveness rather than at the
Python call site.

## 5. `torch.compile`: FX graph to one StableHLO program

TorchTPU registers a TorchDynamo backend named `"tpu"`:

[`src/torch_tpu/_internal/compile/__init__.py:30-31`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/src/torch_tpu/_internal/compile/__init__.py#L30-L31)

```python
registry.register_backend(compiler_fn=TpuBackend(), name="tpu")
```

User code can therefore request:

```python
compiled_model = torch.compile(model, backend="tpu")
```

TorchDynamo captures an FX `GraphModule`. TorchTPU traverses that graph while
deferring all operations, producing one StableHLO compilation unit instead of
materializing each eager operation. The C++ extraction path includes
`ExtractMlirFromGraph` and `TraverseAndCompile` in
[`compiled_mode.cc`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/internal/compile/compiled_mode.cc#L298-L356).

The paper explicitly explains why TorchTPU did not begin as a TorchInductor
backend:

- eager and compiled execution can share the same StableHLO builders;
- XLA's TPU optimization stack is mature;
- Triton's thread/block programming model is designed around GPUs and is not
  a natural match for TPU execution; and
- one direct path avoids translating Inductor's loop-level IR into another
  tensor compiler.

This does not mean Inductor-style scheduling is universally wrong. It means
TorchTPU chose to preserve tensor operations and rely on the TPU compiler
already behind PjRt.

### Dynamic shapes remain a hard boundary

The current compiled path described by the paper forces `dynamic=False`.
Bounded dynamism is under development:

1. a symbolic size becomes a scalar tensor input;
2. the physical tensor is padded to an upper bound;
3. metadata records the logical dimension;
4. XLA's `DynamicPadder` ensures padded elements use the correct identity
   values; and
5. operations carry the logical size through the graph.

OpenXLA exposes the
[`DynamicPadder`](https://github.com/openxla/xla/blob/281e9b28cd39f170ab09656ad4c0f2b9be617605/xla/hlo/transforms/dynamic_padder.h#L70)
pass, while TorchTPU contains its dimension-size operations in
[`dynamism_ops.cc`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/internal/dynamism/dynamism_ops.cc#L120-L260).

Padding enables executable reuse, but it can waste memory and compute. This is
the familiar compiler tradeoff between shape specialization and generality.

## 6. The actual compilation boundary: PjRt

TorchTPU constructs a TPU PjRt client through:

[`csrc/pjrt/pjrt_client.cc:31-42`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/pjrt/pjrt_client.cc#L31-L42)

```cpp
xla::GetCApiClient("tpu", ...)
```

Compilation then reaches functions such as `Compile` and
`CompileAndLoadMlirModule` in
[`compilation.cc`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/common/compilation.cc#L239-L280).

PjRt defines a portable client/runtime contract. The open C API describes a
program and a client compile request in:

[`xla/pjrt/c/pjrt_c_api.h:741-775`](https://github.com/openxla/xla/blob/281e9b28cd39f170ab09656ad4c0f2b9be617605/xla/pjrt/c/pjrt_c_api.h#L741-L775)

Conceptually:

```text
PJRT_Program {
    code
    format
}

PJRT_Client_Compile(client, program, compile_options)
    -> PJRT_LoadedExecutable
```

The TPU-specific header exposes `GetPjrtApi()`:

[`pjrt_c_api_tpu.h:36`](https://github.com/openxla/xla/blob/281e9b28cd39f170ab09656ad4c0f2b9be617605/xla/pjrt/c/pjrt_c_api_tpu.h#L36)

That declaration is open; its production implementation is supplied by
`libtpu`.

### Why `libtpu` matters

The Python package depends on `libtpu`, configures its library path, and then
uses the TPU PjRt plugin. `libtpu` is distributed as a binary package under
Google Cloud terms rather than as an open-source GitHub repository.

Therefore:

```text
StableHLO / Mosaic payload
        │
        │ open PjRt API
        ▼
libtpu binary
        │
        │ closed TPU optimization and code generation
        ▼
TPU executable using a proprietary ISA
```

The paper itself says the TPU ISA is proprietary, subject to change, and not
publicly available. The final fusion, layout, scheduling, instruction
selection, and machine-code generation pipeline cannot be followed in public
source in the same way that LLVM NVPTX and PTX can.

This does not make the open code unimportant. It establishes and transforms
the program that the closed compiler receives: operations, shapes, precision,
sharding, dynamic bounds, custom calls, and collective structure.

## 7. Pallas and Mosaic: the custom-kernel path

StableHLO is designed for graph-level ML operations. A performance-critical
kernel sometimes needs a lower-level programming model.

Pallas provides a Python kernel language in JAX. On TPU, Pallas lowers through
Mosaic. The open source includes:

- Pallas tracing and lowering rules;
- the Mosaic TPU dialect's operation/type definitions;
- serialization of a Mosaic module;
- a `tpu_custom_call` wrapper; and
- TorchTPU integration that exports a Pallas kernel for TPU.

The important path is:

```text
Pallas Python kernel
  -> JAXPR
  -> Mosaic TPU MLIR
  -> serialized MLIR bytecode
  -> stablehlo.custom_call @tpu_custom_call
  -> PjRt / libtpu
  -> TPU executable
```

JAX registers the custom-call primitive in
[`tpu_custom_call.py`](https://github.com/jax-ml/jax/blob/928f647c7ee58502e2eb08e2963cfed98d544f1e/jax/_src/tpu_custom_call.py#L84)
and emits `mlir.custom_call("tpu_custom_call", ...)` around
[`lines 466-478`](https://github.com/jax-ml/jax/blob/928f647c7ee58502e2eb08e2963cfed98d544f1e/jax/_src/tpu_custom_call.py#L466-L478).

Pallas-to-Mosaic lowering is implemented in
[`jax/_src/pallas/mosaic/lowering.py`](https://github.com/jax-ml/jax/blob/928f647c7ee58502e2eb08e2963cfed98d544f1e/jax/_src/pallas/mosaic/lowering.py#L1671),
with a table of operation lowering rules earlier in the file.

The Mosaic TPU dialect definitions now live in OpenXLA XLA under
[`xla/mosaic/dialect/tpu/`](https://github.com/openxla/xla/tree/281e9b28cd39f170ab09656ad4c0f2b9be617605/xla/mosaic/dialect/tpu).
The definitions include operations for reductions, stores, semaphores, and
collectives.

TorchTPU exposes a Pallas bridge through `torch.tpu.pallas.jax_op`. Its source
exports JAX code for the TPU platform:

[`pallas.py:1066-1070`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/src/torch_tpu/_internal/pallas/pallas.py#L1066-L1070)

TorchTPU can also build a `tpu_custom_call` carrying a base64-serialized Mosaic
kernel in
[`mosaic_custom_call.cc:65-78`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/csrc/experimental/precompiled_kernels/mosaic_custom_call.cc#L65-L78).

### The Mosaic dialect is open; the Mosaic compiler is not fully open

This distinction is easy to miss. The public dialect tells us what operations
and types a Mosaic module may contain. The public JAX code shows how a Pallas
program becomes that module and how it is serialized.

The complete production lowering from Mosaic into TPU machine code was not
present in the pinned open trees examined for this article. The serialized
payload crosses into `libtpu`, just like StableHLO.

Mosaic is therefore more analogous to an open target-facing IR than to a
fully open LLVM-style hardware backend.

## 8. Inspect StableHLO without owning a TPU

The open frontend and IR can be explored on a CPU machine. This example asks
JAX to lower a matrix multiplication and prints the StableHLO module:

```python
import jax
import jax.numpy as jnp


@jax.jit
def matmul(a, b):
    return a @ b


a = jnp.ones((64, 32), dtype=jnp.bfloat16)
b = jnp.ones((32, 128), dtype=jnp.bfloat16)

lowered = matmul.lower(a, b)
print(lowered.as_text())
```

The relevant operation resembles:

```mlir
%0 = stablehlo.dot_general %arg0, %arg1,
    contracting_dims = [1] x [0]
    : (tensor<64x32xbf16>, tensor<32x128xbf16>)
      -> tensor<64x128xbf16>
```

This proves only the frontend lowering. Running it with a CPU JAX installation
does not invoke the TPU backend or reveal TPU machine instructions.

### Inspect a Pallas kernel and run it in interpretation mode

A small Pallas add kernel can run through the interpreter on CPU:

```python
import jax
import jax.numpy as jnp
from jax.experimental import pallas as pl


def add_kernel(x_ref, y_ref, output_ref):
    output_ref[...] = x_ref[...] + y_ref[...]


def add(x, y):
    return pl.pallas_call(
        add_kernel,
        out_shape=jax.ShapeDtypeStruct(x.shape, x.dtype),
        interpret=True,
    )(x, y)


x = jnp.ones((8, 128), dtype=jnp.float32)
print(add(x, x))
```

Removing `interpret=True` and exporting for `platforms=["tpu"]` can produce a
StableHLO module containing `stablehlo.custom_call @tpu_custom_call`, whose
backend configuration carries serialized Mosaic MLIR. That export still does
not generate a TPU executable; `libtpu` performs the unavailable final
compilation.

## 9. Distributed execution exposes MPMD versus SPMD

TorchTPU integrates collectives through PyTorch's `c10d::Backend` and lowers
them to StableHLO collective operations. Unlike CUDA, there is no NCCL layer
separate from the TPU compiler.

The difficult part is the mismatch between:

- **MPMD PyTorch execution:** each process can independently reach a
  collective; and
- **SPMD TPU compilation:** all participating devices must agree on one
  globally consistent program.

If different ranks compile different collective structures, execution can
deadlock or corrupt memory.

TorchTPU's conservative default uses **skinny collectives**: compile each
collective as a small separate StableHLO module. The paper reports a 30–40%
end-to-end cost for this safety.

The `@spmd_safe` mechanism marks a region whose processes are expected to
execute the same structure:

[`spmd_util.py`](https://github.com/google-pytorch/torch_tpu/blob/4a22cca20cb3fe1a3f95704df63e81f5dc75fd11/src/torch_tpu/_internal/distributed/spmd_util.py#L46)

This can fuse collectives with surrounding computation, but correctness now
depends on the user's SPMD claim. The paper also discusses a compile handshake
as a future safer mechanism.

## 10. What is open source, exactly?

| Layer | Open? | What can be inspected |
|---|---:|---|
| PyTorch, ATen, Dynamo, FX | Yes | Capture, dispatch, graph breaks, decompositions |
| TorchTPU | Yes | Eager runtime, deferred ops, StableHLO builders, cache, distributed integration |
| StableHLO | Yes | ML operation semantics and serialization |
| OpenXLA XLA | Largely yes | HLO infrastructure, PjRt APIs, many generic transformations |
| Pallas frontend | Yes | Kernel tracing and operation lowering |
| Mosaic TPU dialect | Yes | TPU-facing MLIR operations, types, and serialization |
| TPU PjRt interface | Yes | Client/plugin API contract |
| `libtpu` implementation | No public source | Production TPU compiler and runtime plugin |
| TPU ISA | No | Proprietary machine interface |
| Final TPU executable | No readable public form | Loaded and executed through the runtime |

OpenXLA contains real compiler infrastructure, but its open tree should not be
mistaken for the complete production TPU backend. An open API declaration such
as `PJRT_Client_Compile` tells us how compilation is requested, not how the TPU
compiler implements fusion, layout, scheduling, or instruction selection.

Likewise, an open Mosaic operation definition tells us what an input program
can express, not how that operation maps to a proprietary instruction.

## 12. Results reported by the paper

The paper reports broad framework coverage and large-scale results:

- 4,821 of 4,917 Hugging Face model tests completed without crashing;
- 638 of 657 tested models met the paper's numerical-parity criterion;
- Muse Glimmer 30B reached 59% MFU for single-chip prefill;
- Qwen3 MoE 235B reached 28.8% MFU on 1,024 TPU v7 chips and near-flat weak
  scaling through 16,384 TensorCores;
- FLUX.1-dev improved from 11.49 seconds per step in eager mode to 3.02
  seconds with `torch.compile`, then 2.78 seconds with additional peephole
  rewrites; and
- TorchRec reached parity with the cited JAX baseline on SparseCore.

These figures establish that the architecture can support real workloads, but
they should be interpreted carefully:

- the authors report the results;
- the article does not independently reproduce them;
- model "coverage" includes a no-crash tier and tolerance-based numerical
  checks rather than identical outputs;
- optimized Pallas and library kernels contribute substantially to peak
  performance; and
- the paper does not provide a complete ablation against PyTorch/XLA or every
  alternative backend.

## 13. Current limitations

The paper identifies or implies several constraints:

1. bounded dynamic shapes are still under development;
2. compiled mode currently forces static specialization;
3. one process is used per TPU device;
4. MPMD collective safety remains difficult;
5. skinny collectives impose a reported 30–40% cost;
6. overlapping or broadcast view writes are unsupported;
7. FlexAttention was not supported in the reported TorchTitan port;
8. custom Pallas or library kernels remain important for peak performance;
9. the TPU ISA and final backend are unavailable for inspection; and
10. the codebase and paper are evolving rapidly.

The paper's v4 architecture is therefore a snapshot, not a finished static
contract.

## Closing perspective

TorchTPU demonstrates that "eager" and "compiled" do not need to be opposing
execution models. Strict eager can compile one deferred StableHLO operation at
a time, DeferAndFuse can compile a short region, and `torch.compile` can hand
the same infrastructure an entire FX graph.

The source-visible path is:

```text
PyTorch ATen or FX
  -> TorchTPU deferred operations
  -> StableHLO
  -> PjRt API
```

The custom-kernel path is:

```text
Pallas
  -> Mosaic TPU MLIR
  -> tpu_custom_call
  -> PjRt API
```

Both paths then cross the same boundary:

```text
PjRt
  -> libtpu
  -> proprietary TPU compiler and ISA
```

That boundary determines what open-source compiler engineers can study. We can
inspect PyTorch semantics, graph capture, StableHLO construction, deferred
materialization, caching, dynamic-shape encoding, collectives, and Mosaic
payload generation. We cannot inspect the final TPU instruction selection or
machine-code pipeline.

For practical learning, the best approach is therefore:

1. print StableHLO from a small operation;
2. trace its TorchTPU builder and materialization path;
3. inspect the PjRt compile request;
4. build a Pallas kernel and inspect its Mosaic custom call; and
5. treat the final `libtpu` compilation as a documented but closed boundary.
